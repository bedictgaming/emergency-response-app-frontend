# Emergency Response Client

Next.js progressive web app for Cordova's emergency-response workflow.

## Setup

1. Copy `.env.example` to `.env.local`.
2. Set `NEXT_PUBLIC_API_URL` to the API URL reachable by browsers.
3. Run `npm ci` and `npm run dev`.

## Build and PWA preview

```text
npm run lint
npm run build
npm run preview:pwa
```

The client includes a service worker for static-shell resilience. Emergency submissions intentionally require connectivity because the server must verify proof photos and prevent duplicates before accepting a report.

## Release gates and browser tests

### October 1 release contract (supersedes older deployment notes below)

The default, public and validation Vercel configurations now use platform Routing Middleware at `/api/:path*`, not unsigned API rewrites. The server-only gateway signs the original path/query, caller IP and session/origin context. Vercel production can target only the production Railway API and `emergency-response-production-v1`; preview can target only synthetic staging and its distinct audience/key. Missing or mismatched runtime settings fail closed with 503. Both gateway and backend must have matching server-only `API_GATEWAY_SECRET` and `API_GATEWAY_AUDIENCE`; the gateway also requires the fixed `API_GATEWAY_UPSTREAM`. Never expose these values through `NEXT_PUBLIC_` variables or reuse a staging key in production.

Use explicit public-build mode flags and the exact Cordova first-party API origin with `npm run deploy:build`. A public-mode build is not public access authorization: retain All Deployments protection through paired rollout and browser/device acceptance, then use Standard Protection so only production domains are public. Keep the previously working paired gateway/backend configuration for rollback; an older unsigned frontend is incompatible with backend gateway-required mode. Do not disable backend enforcement to make a failed public deployment appear healthy.

Signed direct photos use Cloudinary `/image/upload` with signed `type=authenticated` and support originals up to 5 MiB. If the browser blocks that transfer, the authenticated base64 fallback is limited to 2.5 MiB originals and a 3.5 MiB JSON request; larger photos show a recoverable error without submitting the report or altering evidence. Login/permission/rate-limit failures do not bypass the signature endpoint through fallback.

The October 1 checks passed 125 mocked Chromium workflows, four targeted upload regressions after the endpoint correction, 14 native deployment/gateway tests, lint, TypeScript and a fresh public-mode export. Bounded real synthetic staging checks also passed all four departments plus multi-service routing, private original download, refresh/logout, and event streaming through Vercel. These are not production peak-capacity, OAuth, email/push or physical-device certification. Production deployment and access acceptance are recorded separately in the workspace release log.

`npm run release:check` rejects local or placeholder API endpoints before a PWA deployment. It does not publish the app.

The Vercel project remains protected by Vercel Authentication on **all** deployment URLs. The old default configuration used a reserved `.invalid` API origin; do not assume older saved cloud values have been corrected. Vercel CLI linkage lives in ignored `.vercel/`; never commit `.env.local`.

As of the October 1 local remediation, `vercel.json`, `vercel.public.json` and `vercel.production-validation.json` share the live first-party API rewrites, no-store policy and CSP. Their `npm run deploy:build` command fails before building unless `NEXT_PUBLIC_API_URL` is exactly the Cordova origin and all four mode flags are explicit. For a public candidate set public-launch `true` and production-validation, preview-only and staging-test `false`. For protected production validation set production-validation and preview-only `true`, public-launch and staging-test `false`. `npm run test:deployment` checks these modes and the config parity. Vercel's `npm run build` prebuild also validates modes when `VERCEL=1`, guarding build-command overrides. The explicit legacy `vercel.staging.json` can still build with the exact synthetic-only staging API, staging-test/preview-only `true` and the other two flags `false`; default `deploy:build` rejects that staging mode. Local development and mocked browser builds are unaffected. These changes are not deployed automatically, do not set cloud variables and never change deployment protection. A unique preview domain still cannot complete the exact-origin production cookie/OAuth flow.
`vercel.staging.json` is an explicit, protected test-deployment configuration: its CSP allows only the Railway staging API, Cloudinary, and Nominatim. Build it with `NEXT_PUBLIC_API_URL` set to the staging HTTPS origin, `NEXT_PUBLIC_STAGING_TEST=true`, and `NEXT_PUBLIC_PREVIEW_ONLY=true`. The banner then states that test reports are not emergency requests.
`vercel.production-validation.json` is for a protected validation build against the live Railway API. It forwards both trailing-slash and slashless `/api/:path*` requests to `https://api-production-49dea.up.railway.app/api/:path*` without caching API responses. Both rewrite forms are necessary: the initial proxy sent list URLs ending in `/` to Vercel's own 404 instead of Railway. Build it with `NEXT_PUBLIC_API_URL=https://cordova-emergency-response.vercel.app`, `NEXT_PUBLIC_PRODUCTION_VALIDATION=true`, and `NEXT_PUBLIC_PREVIEW_ONLY=true`. The `prebuild` lifecycle enforces these values even if Vercel project settings override the local config's build command. For OAuth and protected evidence to use first-party cookies, the backend `BACKEND_URL` is the exact Cordova alias and that alias's `/api/auth/v1/google/callback` is registered on the Google OAuth client. On 29 September 2026, these coordinated settings were applied to the protected Cordova alias. A user-observed Google sign-in reached the citizen dashboard; read-only proxy checks confirmed unauthenticated incident requests return Railway's `401`, alerts return `200`, and both API path forms route correctly. An authenticated report-list read, evidence workflow, and incident delivery still require browser validation. Vercel Authentication redirects the manifest to a cross-origin SSO URL that cannot be loaded under its CORS policy, so this protected validation build omits the manifest link, unregisters any old service worker, and hides installation controls. Ordinary builds still include the same PWA manifest and service worker. The banner warns that test submissions affect the live system. The Cordova Vercel alias remains behind Vercel Authentication. A unique preview URL cannot complete credentialed API workflows because the backend admits only the exact Cordova frontend origin and the OAuth callback is bound to that alias. Keep Vercel Authentication on and coordinate any real-data test before submitting; never use this build as the public release. A public production build requires a separate approved configuration and completed release gates.

`npm run test:e2e` builds the static export and tests it on an isolated local server at port 3100. The browser workflow tests mock API/Cloudinary responses; they do not create emergency reports, upload real photos, or send notifications. They are not a substitute for staging integration and physical-device tests.

Failed submissions retain their fields and proof photo while the form remains open. Drafts are not persisted across reloads. Offline submissions are not marked as accepted.
